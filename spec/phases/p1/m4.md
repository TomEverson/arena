**Phase:** 1 (FFA Deathmatch) · **Status:** code complete, awaiting playtest in two tabs · **Depends on:** M3

## Done when
Two browser tabs see each other move smoothly at 80 ms and 3% loss, with no visible rubber-banding.

## What was built
- **Protocol** (`protocol/messages.json` + `scripts/gen.mjs`): one schema generates the Go and TS types, including the movement `Input` and `PlayerState`. New messages: `input` (last 3 inputs per message), `ping`/`pong`, `respawn`; `welcome` now names the level; `snapshot` carries your full state (`you`), `ackSeq`, `queued` and everyone else as `Entity` (position, yaw, pitch, posture flags). Details in `protocol/README.md`.
- **Server is input-driven**: a player only moves when an input arrives (one per tick), so its state is always exactly "after input ackSeq". A lag spike is caught up with a second input per tick, paid for with banked credit (about 8 extra ticks, regaining 1 per 20 ticks) so flooding inputs cannot speed-hack. Duplicate sequence numbers are skipped. `respawn` resets the player and keeps queued inputs.
- **Prediction** (`client/src/net/prediction.ts`): pure `Predictor`. `step` simulates immediately and records each input; `reconcile(ackSeq, you)` compares with its own state at that ack, and on a mismatch adopts the server state and replays unacknowledged inputs. `smoothing.ts` fades small corrections out of the camera and snaps big ones (over 2 m).
- **Remote players** (`interpolation.ts`, `clock.ts`, `remoteView.ts`): the server tick is estimated from snapshot arrivals; others are drawn 6 ticks (100 ms) in the past, interpolated, as coloured box figures that crouch and slide.
- **Browser** (`main.ts`): connects to `/ws`, starts predicting from the first snapshot, sends inputs every tick. With `?offline` (or no server) it falls back to the local simulation so tuning still works. P now asks the server to respawn. The HUD shows ping, jitter, snapshots per second, the server's queue, unacknowledged inputs, and prediction corrections.
- **Dev**: `pnpm dev:lag` runs the client and a server with `--fake-latency=80ms --loss=3%`. Note the flag is per direction, so 80 ms is a 160 ms round trip.

## How it was checked
- 24 unit tests of the netcode against a simulated network: no corrections at 160 ms RTT with jitter and 3% loss, none even at 500 ms one-way with jitter, convergence under 40% loss, and a clean snap on a server-side respawn.
- Go: WebSocket integration tests (welcome, ping, redundant inputs simulated exactly once, respawn, garbage ignored), input-driven and catch-up-budget tests, codec tests, the zero-allocation test.
- `pnpm netcheck [seconds] [latency] [loss]`: two headless players built from the same client classes against the real Go server. At 80 ms / 3% over 15 s: 0 corrections for both across about 478 snapshots each, round trip 161 ms, 1,002 frames of remote motion with no pops.

## Known limits
- Weapons and dummies are still client-only: other players cannot be shot yet (M5).
- Duplicate-skipping assumes in-order delivery (true for WebSocket).
- No clock-speed adaptation: if the server queue grows, the player only sees a little extra latency; the `queued` field and HUD show it.
- Remote players are placeholder boxes; no names or weapons.
